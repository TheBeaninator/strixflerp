# ABI differences: strix-trellis C API v1 against StrixFold's dsv41 kernel ABI

What an adapter has to bridge to run a strix-trellis EXL3 linear where StrixFold runs one of its own. Card
ORIGIN-TRELLIS 41e8802da1. Read from source only; nothing here was compiled, linked or run.

- **strix-trellis**: `include/strix_trellis.h` at a34516b (531 lines, `STRIX_TRELLIS_ABI_VERSION` 1, library 0.3.0),
  in the catalogue as `catalog/strix_trellis/kernel/c_api/src/include/strix_trellis.h`; contract text in the origin's
  `docs/API.md`, `docs/DENSE_R1.md` and `docs/TP_RANK.md` (not copied). Cited below as `st.h:<line>`.
- **StrixFold**: `zig/kernels/hip/dsv41/abi.h` at f64b5ff (411 lines, `TF_DS_HIP_ABI_VERSION` 1), in the catalogue as
  `catalog/strixfold/kernel/dsv41_abi/src/zig/kernels/hip/dsv41/abi.h`, with the kernels that take its structs in
  `catalog/strixfold/kernel/exl3/src/zig/kernels/hip/dsv41/exl3.hip`. Cited as `abi.h:<line>` and `exl3.hip:<line>`.

The two headers describe different layers. `abi.h` is a kernel ABI: the by-value argument structs of device kernels
that StrixFold's Zig host launches itself. `strix_trellis.h` is a library ABI: opaque handles and host functions
that launch the library's own kernels. Every difference below follows from that or from the numerics.

## Differences

| # | Subject | strix-trellis (`st.h`) | StrixFold (`abi.h`, `exl3.hip`) | What the adapter does |
|---|---|---|---|---|
| 1 | Layer and linkage | Host C functions over opaque handles (`strix_context`, `strix_weights`, plan handles, st.h:113-117); a static library `libstrix_trellis.a` that links `hip::host` and launches C++ template kernels with `<<< >>>` | Device kernels with `extern "C"` names, compiled device-only to one gfx1151 code object a source, loaded as a manifest-described kit and bound by id (`exl3.glinear`, `exl3.rot_many`, `exl3.gemm`); the Zig host packs the argument struct and launches | Cannot be a kit entry. The adapter is host code: a C shim linked into the StrixFold binary (Zig `linkLibrary` plus the HIP runtime), called at the launch sites of `exl3_linear.zig` / `exl3_prefill.zig` in place of the kit launch. StrixFold's kit manifest check (`gpu/hip/kit.zig`) does not cover it, so the library needs its own identity check (version call, st.h:264) |
| 2 | Versioning and descriptor rules | `STRIX_TRELLIS_ABI_VERSION` 1 in every descriptor, with `struct_size`, zeroed reserved fields, enums and pointers as members (st.h:11-15); mismatches return `STRIX_ERROR_ABI_MISMATCH` at run time | `TF_DS_HIP_ABI_VERSION` 1 shared by kit and binary; fixed-width members only, `uint64_t` device addresses, no pointer, enum or bool, explicit padding, a size and offset assertion per struct at compile time (abi.h:1-12) | Fill descriptors field by field from the Zig side through `@cImport` of `strix_trellis.h`; do not mirror them as Zig structs the way `hip_load.zig` mirrors `abi.h`, because the header carries no layout assertions |
| 3 | Who owns the weights on the device | `strix_weights_prepare` / `_prepare_parts` copy trellis, `suh`, `svh` and optional bias from host memory into one persistent device allocation in a private layout and return a handle (st.h:271-278); `strix_weights_device_span` gives a read-only view (st.h:283) | The caller owns device memory and passes raw addresses per launch: `T`, `svh`, `bias` in `tf_ds_exl3_glayer` (abi.h:65-93), `suh` in `tf_ds_exl3_rlayer` (abi.h:137-146), pointer tables to checkpoint-layout trellises for experts (abi.h:216-234) | The largest change. Either StrixFold's loader hands the host regions of each tensor to `strix_weights_prepare_parts` and drops its own upload of those tensors, or the weights are on the device twice. No entry takes an existing device address. PLACE / engram staging is unaffected (host bytes are the same), but StrixFold's `exl3.l2_prefetch` ranges (abi.h:397-404) would have to come from `strix_weights_device_span` |
| 4 | Trellis bytes | Transport v1: little-endian 16-bit containers `[I/16, N/16, 16*bits]`, tile order kept at upload (docs/API.md, transport table); kernels read `const uint32_t*` | Checkpoint layout read as `const uint32_t* T`, MSB-first, 4 K2 u32 words a tile (exl3.hip:19-21) | Same file bytes on both sides as far as the two descriptions go; confirm on one tensor with the CPU reference (`tool.strix_trellis.reference`) before trusting it |
| 5 | Bit rates | `bits_x2` even only: integer 1 to 8 bits (st.h:62); fractional rates rejected | K2 half-bits as a template argument; the built glinear variants are K2 4, 6, 8, 10, 12, 16 (exl3.hip:728-739), gemm 8, 10, 12, 16 (exl3.hip:1038-1045) | Every built StrixFold variant is an integer rate, so the limit does not bite today; the adapter must refuse an odd K2 rather than round it |
| 6 | Codebooks | 3inst, mcg and mul1 by enum plus exact marker (st.h:51-55, 21-23); the measured fast paths are mul1 | mul1 only (`0x83DCD12D`, exl3.hip:9) | Pass `STRIX_CODEBOOK_MUL1` with `STRIX_EXL3_MARKER_MUL1`; nothing to bridge |
| 7 | Activation and output types | F32 only, contiguous row-major, original basis; F16 / BF16 enum values are reserved and rejected (st.h:135-147) | Input fp16, bf16 or fp32 (`x_dtype`, abi.h:137-146); output fp16, bf16 or fp32 (`y_dtype`, abi.h:65-93, `enum DType` exl3.hip:38) with the rounding to the stored type inside the epilogue | StrixFold's residual rows are bf16. The adapter needs an F32 view in and a rounding kernel out (a launch each side), or strix-trellis needs bf16 tensors upstream. A conversion launch per linear cancels part of the gain on small projections |
| 8 | Where the input rotation runs | Inside the operator: `X * suh` rounded to fp16, H128, rounded to fp16, either as an `input_transform` launch into the workspace or fused into the core (docs/API.md "Operation and orientation") | A separate kernel, `exl3.rot_many`, rotates the inputs of up to 8 layers in one launch into `xh` fp16 buffers that glinear then reads (abi.h:137-162, exl3.hip:706-707) | Call strix-trellis with the unrotated activation and skip `rot_many` for that layer; a rotated `xh` cannot be handed in |
| 9 | Epilogue | H128, `svh`, optional bias, then `alpha * Linear(X) + beta * Y` (st.h:149-166); nothing else | H128, `svh`, bias, then optionally RoPE on the output (`rcos`, `rsin`, `rpos`, `rhd`, `rrd`) and optionally the next layer's input rotation written from the rounded output (`rsuh`, `rxh`, `ldr`, `roff`) (abi.h:65-93, exl3.hip:426-460) | Layers that use the fused RoPE or the chained rotation need those steps as extra launches after strix-trellis returns, in the same rounding order (output rounded to its stored type first, exl3.hip:426) |
| 10 | Grouping | One linear a call. Grouped forms are narrow: `strix_grouped_gemv_plan` takes up to 8 linears of one geometry, admitted for 4096 to 1024 at K4 / K5 (st.h:415-450); the dense pair takes q_a and kv over one input (st.h:341-351) | One glinear launch carries up to 8 different layers (`TF_DS_EXL3_GMAX`, abi.h:62; `tf_ds_exl3_gargs` 1,424 bytes, abi.h:124-130), each with its own shape, K, split count and epilogue | A StrixFold group becomes several strix-trellis submits unless it happens to be one of the two admitted shapes; count launches per decode step before and after, because the launch floor is what small projections pay |
| 11 | Rows | `strix_gemv` 0 to 8 rows; `strix_gemm` rank 2 with any row count; TP plans 1 to 8 rows (st.h:151, 186-188) | glinear below 64 rows with dot2, wide blocks from `EXL3_WIDE_MIN` 64 (exl3.hip:463-472, 620); gemm variants m128 and m256 for prompt chunks (exl3.hip:1038-1045) | Decode and verify windows of 9 to 63 rows have no GEMV on the strix-trellis side: route them to `strix_gemm` (other fp32 reduction order, see 12) or keep StrixFold's kernel for them |
| 12 | Accumulation order and row invariance | Split count chosen per shape, bit width and row count (`src/gemv_policy.hpp`), so a row's bits through `strix_gemv` can depend on how many rows share the call; the dense R1 plans and grouped GEMV fix every row to its single-row bits under a declared identity (`STRIX_DENSE_R1_S4` / `_LEGACY`, st.h:394-395; `STRIX_GEMV_ROW_INVARIANT_R1`, st.h:431) | Row-invariant by construction: each row in the same order whatever the window's width, split-K partials and wave sums added in a fixed order (exl3.hip:8-16); contract `exl3.linear` of numerics.json is a tolerance against the CUDA bits | Neither side's bits equal the other's. A swap has to pass StrixFold's `exl3.linear` tolerance and its replay gate, and draft verification must use the row-invariant plans, not plain `strix_gemv`, or drafts can change output |
| 13 | Scratch and split-K state | One caller-owned workspace a call, 256-byte aligned, size from `strix_matmul_workspace_bytes` (st.h:20, 285); plans keep arrival counters at the start of their workspace, zeroed at creation and left zero | Per layer: `Z` partial planes and `counters` passed by address, counters left zero by the block that completes a column block (abi.h:65-93, exl3.hip:573) | Size and allocate the workspace once per plan from StrixFold's scratch arena; StrixFold's `Z` and `counters` for that layer go unused |
| 14 | Streams and completion | Borrowed `hipStream_t` in `strix_stream`; submit status covers validation and enqueue only, no synchronisation (st.h:120-125, 525-527) | Launches on the Zig host's stream, in order; no PDL (exl3.hip:23-24) | Pass StrixFold's stream. Plans freeze pointers, shapes and the stream (st.h:291-303), so buffers that StrixFold reallocates between steps force a plan re-create |
| 15 | Tensor parallelism | Per-rank plans over local shapes; the output is a local contribution and the inter-rank reduction is the caller's (st.h:182-186, 215); a bias belongs to one rank only | StrixFold runs each rank's linears on that rank's slice and reduces through its collectives (`coll.hip`, abi.h:332-350) | Check that StrixFold's two-rank split of each projection is the split the origin's per-rank shapes assume (README "Per-rank shapes": q_b halves the outputs, o_b halves the inputs) before using the TP plans; not verified on this card |
| 16 | Routed experts | `strix_tp_moe_*`: K2 / K3 mul1, top-6 fixed (`STRIX_TP_TOP_K` 6, st.h:187), F32 `[R,5120]` in and out, SiLU, scores not normalised (st.h:213), no clamp unless built with `STRIX_TRELLIS_TP_MOE_DECLARED_SWIGLU`; host or device routes; a bank of 6 to 256 experts | Decode: `grouped_cp` with an epoch / ready protocol and `tf_ds_exl3_decode_epi` (clamp `limit`, `act_mode`, bf16 rounding, abi.h:168-191). Prefill: `tf_ds_exl3_pf_args` with per-expert K2 tables, fp16 / bf16 input, jobs of up to 128 rows (abi.h:216-234) | Not a drop-in: the activation (clamped SwiGLU against SiLU), the rounding points, the bank size (StrixFold routes over 384 experts, abi.h:362) and the row range differ. Out of scope for a linear adapter; a separate experiment if the dense swap pays |
| 17 | Errors | `strix_status` codes from every call (st.h:25-35); asynchronous device errors through HIP | Kernels return nothing; the Zig launcher checks the HIP launch | Map a non-success status to StrixFold's launch failure path and fall back to the kit kernel for that layer |

## What carries over without an adapter

- The checkpoint: the same EXL3 safetensors bytes feed both (rows 4 to 6), so no conversion and no second set of
  weights in cold storage.
- The mul1 decode itself: both multiply the state by `0x83DCD12D` and sum bytes; StrixFold decodes a 16 x 16 tile once
  a wave, strix-trellis keeps per-lane windows (`src/packed_decoder.hpp`). That is a shape to compare inside
  StrixFold's own kernels with no ABI work at all.
- The CPU reference (`tool.strix_trellis.reference`) runs on control-node's CPU against any tensor of the served
  checkpoint and names each rounding stage, which is what row 12 needs first.

## Smallest adapter that answers the question

One dense projection, decode only: q_b on one rank through `strix_tp_dense_plan_create_r1`, with rows 3 (prepare
from host regions), 7 (F32 in, bf16 out) and 12 (tolerance gate) bridged and everything else left on StrixFold's
kernels. That needs the pair up, a build of `libstrix_trellis.a` with TheRock on a worker and a timed comparison on
the same tensors; it is an experiment card of its own and was not started here.
