## How it was made, and how to redo it

```
python3 docs/harvest/harvest_<origin>.py      # each script rebuilds catalog/<origin> from the reference checkout
tools/pod-push.sh --card <card-id> && tools/pod-run.sh 'python3 gate/compile/run.py' && tools/pod-pull.sh gate/results
python3 docs/harvest/harvest_<origin>.py      # again: gate.status = "builds" is written from gate/results/compile
python3 docs/harvest/make_harvest_md.py && python3 flerp check
```

- `docs/harvest/harvestlib.py`: copying, manifest writing, include-derived `requires`, the `unharvested` list for `flerp diff-origin`.
- `docs/harvest/incgraph.py`: `#include` closure, used to give shared headers to header-only modules (gufo, hipfire).
- `docs/harvest/hipfire_units.py`: recovers hipfire's compile units from the Rust source constants and sorts kernel sources into families.
- `docs/harvest/hipfire_exclusions.py`: turns compile failures with a known cause into `docs/harvest/data/hipfire/not_gfx1151.json`.
- `docs/harvest/data/strixfold/`: `aot.json` (the Triton kit manifest), `tri-SHA256SUMS` and the HIP kit manifest, fetched from control-node
  (`/data/pod/plans/af9276f296/tri-kit-gfx1151`, `/data/pod/plans/strixfold/fork/zig-out/native-hip/test/dsv41-kit`).

### The kit hashes

The strixfold objects of this gate have the same byte sizes as the ones the origin's `zig build` produced on control-node, but different hashes.
Cause (found in phase 3, reproduced both ways on control-node with TheRock 10.2): clang gives every HIP translation unit a compile unit id,
the symbol `__hip_cuid_<hash>`, and derives it from the **strings of its command line**, the input path and the `-o` path among them. The
hex digits of that symbol name, and with them the order of the dynamic symbol and hash tables, are the only bytes that differ (186 bytes in
`glue.hsaco`). Nothing else enters: no timestamp, no absolute path (the same relative command gives the same bytes in any directory).
`zig build` passes the paths relative to the build root (`./zig/kernels/hip/dsv41/glue.hip`, `-I./zig/kernels/hip/dsv41`) but names the output
`./.zig-cache/o/<digest>/glue.hsaco`, and that digest covers the absolute paths of the step's inputs, so it changes with the location of the
checkout. Hence: workers F and A (same home path) build identical kits; control-node's `fork` and its worktree `af9276f296/wt` do not; and
this gate's own command line (other `-I` and `-o`) gives a third set.

The recipe `dsv41-flash.strixfold-tp2` reproduces the reference deployment's kit byte for byte: `[build.hipcc_output_pins]` records the cache
directory name the reference build (the worktree the deployment on F and A was built in) compiled each object into,
and `flerp assemble` routes hipcc through a wrapper that compiles to that path string and copies the object to where Zig asked. Result on
control-node: 169 objects and the deployment's kit manifest sha256, at each commit cut so far: f44d736 (deployment f44d73633ef5, built in
`af9276f296/wt`, `2776d4b8...72cc`), then ef4c5f7 and f64b5ff (deployments ef4c5f726f54 and f64b5ff2e28b, built in `d74bd09137/wt`, `76936479...8455`).

### Re-cutting StrixFold to the commit the pod serves

The serving build on F and A moves with the pod's own StrixFold work. One command re-cuts the catalogue, the kit pins and the gate's reference:

```
python3 gate/strixfold_recut.py <commit> <deploy-dir-name>      # e.g. f64b5ff f64b5ff2e28b; run on the laptop, re-runnable
tools/pod-push.sh --card <card-id>     # from the card's worktree (tools/card-branch.sh)
tools/pod-run.sh './flerp gate recipe dsv41-flash.strixfold-tp2 --stages check,origin,build'
tools/pod-run.sh './flerp assemble dsv41-flash.strixfold-tp2-abi && build/dsv41-flash.strixfold-tp2-abi/build.sh'
```

It exports the commit from the pod fork (`git archive`), checks that `~/tfp/deploy/<deploy-dir-name>` on worker A is that commit, finds the
worktree whose build is the deployed kit and reads the pins from its Zig cache, re-runs `docs/harvest/harvest_strixfold.py` on the export and
rewrites the pins and the reference in the two recipes, `gate/dsv41-flash.strixfold-tp2.toml` and the gate's base conf. It refuses when the
deployment is another commit or no worktree still holds its build. It reads the pair (ssh, read-only) and does not commit.
The four binaries are not byte-identical to the deployed ones: they carry the absolute path of the build tree (5 occurrences in `tensorfold-native`).
